na51089 bootrom -- annotated vector page and reset path
=========================================================

NT98560/561/562/566 (NA51089) 32 KiB mask ROM, sha256 226408d7...eb19 (see
MANIFEST).  Code is linked to run at 0x00000000; the same 32 KiB is visible at
its home 0x80000000.  Nothing in the ROM refers to 0x80000000: every literal
is a 0x0000xxxx ROM address or an MMIO/SRAM address, so the image is simply
position-dependent at 0.

ISA: the whole image is ARM (A32).  There is no Thumb code: no BX/BLX
to a register anywhere, the only computed branches are `ldr pc` jump tables
and the single `mov pc, r3` that enters the loader, every exported pointer
at 0x7FBC..0x7FEC is even, and a linear ARM decode of 0x0000..0x78D7 has no
undefined encodings outside literal pools.  The earlier rom-thumb.lst
listing is an artefact (Thumb decode of ARM code) and can be discarded.

Layout of the image:

  0x0000..0x031f   start.S: vectors, reset handler, boot dispatch, the
                   loader check/jump (hand-written: no fp frames, shared
                   literal pool at 0x2e4)
  0x0320..0x78d7   C code (gcc, -marm, frame pointers: push {..,fp,lr};
                   add fp, sp, #N), each function followed by its pool
  0x78d8..0x7a4f   const: USB descriptors and strings
  0x7a50..0x7d67   const: Ethernet frame templates, SCSI replies, LZMA
                   message strings
  0x7d68..0x7fbb   0xFF fill
  0x7fbc..0x7fef   exported table (see functions.txt "Data")
  0x7ff0..0x7fff   0xffffffff, "REAL", 0x00000000, 0x00000116

Notes on the reset path

  * No .data/.bss initialisation: the ROM never zeroes or copies its SRAM.
    Every global is written before it is read, by the boot path that owns
    it (see sram.txt).
  * Caches and MMU stay off for the whole ROM run.  The only barrier
    instructions are `dsb sy`: before USB DMA (0x53d4, 0x5ba0) and after
    the USB ADDR_WRITE store (0x5890).  The only CP15 access is the SCTLR
    read-modify-write at 0x64/0x78.
  * The dispatch at 0x1bc is a jump, not a call, and the boot_* functions
    are entered with whatever lr the last `bl` left: 0xd8 (after
    uart0_init_banner) or 0x19c (after the GPIO reset pulse).  None of
    them normally returns -- they end in run_loader or in boot_fail(),
    which calls the next source -- but flash_boot does `return 0` when a
    SPI NAND scan of 256 blocks finds no header, which lands back at
    0xd8/0x19c and re-runs the strap dispatch: an endless rescan, not a
    fallback (inferred from the control flow; not observed on hardware).
  * Fallback is by nested calls: boot_fail -> next_boot_source -> X_boot
    -> boot_fail -> ...  The stack (0xF07D3000 down) is never unwound, so
    each failed source leaves its frame behind (a few hundred bytes per
    round; the 30 s USB/UART timeouts make overflow impractical).

Loader header, as the ROM reads it (offsets from the load address; the first
0x28 bytes are also staged at 0xF0800200 -- see sram.txt):

  +0x00  entry point (jumped to by `mov pc, r3`)
  +0x04  load address (flash/SD/eMMC copy the image there; ETH/USB/UART
         take it from the transport instead)
  +0x0c  DRAM-script log: bit30 = enable, bits[27:0] = log buffer address
  +0x24  loader size in bytes (checksum and load length)
  +0x30  u16 tag 0xAA55
  +0x34  register polled by script op 4
  +0x38  script word: [11:0] entry count, [15:12] extra 512-byte header
         sectors to fetch before running the script, bit16 = transfer
         mode 2 for the body (flash ctx +0 / SD ctx +0; FIFO-DMA select,
         inferred), bit18 = take a new storage clock
         divider from bits[31:24], bit19 = allow script op 7 (training)
  +0x3c  base address for script ops 5 and 9
  +0x40  script entries (2 or 1 words each, see hdr_script_run)
  +0x88  flags: bit31 = trust the controller's hardware checksum,
         bit30 = dual-I/O read for the body (flash), bit29 = check the
         SHA-256 at +0x2e0 (secure boot; read from 0xF07C0088
         whatever the load address), bit28 = copied to 0xF0800400 bit31,
         which switches SPI/eMMC reads to controller DMA straight into the
         destination (inferred)
  +0xc0  RSA-2048 modulus (256 B)           secure boot only
  +0x1c0 RSA public exponent (32 B)
  +0x1e0 RSA signature (256 B, byte-reversed into the engine)
  +0x2c0 AES-encrypted SHA-256 (32 B, 'A' mode)
  +0x2e0 SHA-256 of the image with this field zeroed (bit29 check)
  +0x300..+0x7fff  AES-128-CBC encrypted area ('S' mode)

Checksum: the 16-bit sum over the first size/2 halfwords h[i] of
(h[i] + i) must be 0 and h[0x18] (the u16 at +0x30) must be 0xAA55.  The
flash, SD and eMMC controllers accumulate sum(h[i]) in hardware (SPI +0x58,
SDIO +0x6c); the ROM adds n(n-1)/2 for the index term and passes the result
as hwsum, used only when header+0x88 bit31 is set.
